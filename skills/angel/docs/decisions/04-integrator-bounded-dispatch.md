# Pin the integrator off the volatile default model and bound its dispatch

**Decision**: Pick the integrator's model by one rule — *the smartest model available that doesn't run the meter (incur a separate charge), with the 1M-token window the bundle needs*. As of 2026-06-10 that instantiates as a Fable-first ladder: `claude-fable-5[1m]` when Fable is working and won't incur a separate charge (on-subscription), else `claude-opus-4-8[1m]`, else inline integration in the orchestrator context. **The rule is the binding decision; the specific model IDs are its current instantiation** — re-point them whenever the smartest no-meter [1m] model changes (a new top model, or a billing-status change to Fable). Dispatch background-bounded (≤10-min deadline) so a stall is both prevented (off the volatile tier) and bounded (deadline → inline fallback). Applies to every integrator dispatch — interactive `/angel`, `--loop` cycles, and unattended.

**Why**: The integrator is the lone load-bearing subagent — heaviest, dispatched alone, last, after every persona, with no report if it fails. Dispatched without a model selection it inherited the session default, which became `claude-fable-5` on 2026-06-09. Fable 5 has intermittent availability — observed directly: the Bash safety classifier (also Fable 5) was unavailable for most of the 2026-06-10 debugging session. A single large subagent on a stalling backend, dispatched foreground with no timeout, hangs indefinitely; the orchestrator goes silently quiet (the "delivery-stall blind spot" in CLAUDE.md) until a human hits Esc and integrates by hand. This hung the 2026-06-09 meta run (multi-hour wall) and the 2026-06-10 diff run on a second project; both were rescued by finishing integration inline. Personas don't exhibit it — they batch in parallel with per-persona failure capture (SKILL.md §4), so one stall degrades to a Coverage-Gaps banner, whereas an integrator stall is total. The integrator needs a **1M-token window** for large full/multiball bundles (SKILL.md §1), so the fallback can't simply drop to a 200k tier: Fable[1m] stays the default when healthy and free; Opus[1m] is the fallback that keeps the window off the volatile tier; inline integration (orchestrator runs on Fable[1m]) is the last resort. [ran: classifier "claude-fable-5[1m] is temporarily unavailable" repeatedly, 2026-06-10 session; read: `~/.angel/runs/<run-id>/findings-snapshot.json` for the 2026-06-09 meta run (within_persona_runs:null → not multiball); read: SKILL.md §5 template (no `model:` on the integrator dispatch before this change)]

**Rejected alternatives**:
- *Pin the integrator to bare `opus` (coarse tier).* Dropped after the 2026-06-10 self-review on the belief that coarse `opus` resolves to a 4.x model at **200k**, not 1M (docs/decisions/03 condition 2 as originally written). **Update 2026-06-12**: that premise was wrong — an `opus`-tier probe self-reported `claude-opus-4-8[1m]` [ran], so the coarse tier keeps the 1M window (at least when dispatched from a `[1m]` parent session). The rejection's *conclusion* survives for a different reason: the ladder's explicit selection rule documents *why* each rung is chosen, which a bare tier pin doesn't.
- *Wait for Fable 5 to stabilize and leave the integrator on the default.* Dropped: availability is Anthropic-side and unbounded in time; meanwhile every full-run review risks a silent multi-minute hang invisible to the orchestrator.

**Verification 2026-06-12** — falsifier (a) RESOLVED in the ladder's favor: the `opus` tier self-reports `claude-opus-4-8[1m]` (1M window), so the Opus rung is real [ran: tier probe; caveat — probed from a `[1m]` parent session]. Run-tier test PASSED same day: the 2026-06-12 `/angel --full` meta-run (`~/.angel/runs/<run-id>`) dispatched the integrator background-bounded on `claude-fable-5[1m]`; delivered in 344s (within the 600s deadline) WITH the usage block intact (`integrator.total_tokens: 37991`) — the 06-10 metering-loss concern did not reproduce on this path. Falsifier (b) remains open: watch the next ~5 full runs per below.

**Could-be-wrong-if**: (a) the dispatch surface silently ignores the `[1m]` suffix on Opus and resolves the fallback to a 200k tier — then large full/multiball bundles must route to inline, and the "Opus[1m]" rung is illusory. Check: dispatch a deliberately large full-mode integrator on the Opus fallback and confirm `usage.json` shows a 1M-window model and no truncation. (b) the hangs persist even off Fable — a full-run integrator on `claude-opus-4-8[1m]` still stalls past the 10-min deadline in ≥1 of the next ~5 full runs — meaning the cause is heavy-subagent delivery-stall (harness-level), not Fable availability. Check: across the next 5 full runs, read `usage.json` `integrator.model` and watch for the `integrator: <model> unavailable — integrated inline` note; if it appears with a non-Fable model, reopen.

**How to apply**: Every integrator dispatch (interactive `/angel`, `--loop` cycles, unattended) uses the Fable-first ladder and the background-bounded dispatch + inline (interactive) / minimal (unattended) fallback. The model-selection statement is duplicated across **SKILL.md §1** (integrator paragraph + model-ID note), the **`--model-override`** flag line, the **§5 "Dispatching the integrator"** block (authoritative), the **Notes** footer, and **unattended.md** (the standalone integrator-model line + Step 4) — keep all in sync; `scripts/validate-personas.py` guards the SKILL/unattended model tables. Revisit when Fable 5 stabilizes or new-family models become directly dispatchable (docs/decisions/03 condition 2). Does NOT change persona model tiers: top-tier personas still inherit the default and share the Fable risk, but degrade gracefully via §4 failure capture, so they're out of scope here.
